# Nebius Serverless Jobs for Local Edition: session-only (rewritten 30 Oct 2026, 02:30 MYT)

**The Nebius AI Cloud control plane is never called from Cloudflare.** Team finding, 30 Oct 2026 02:30 MYT: from a deployed
Cloudflare Worker, `auth.eu.nebius.com`, `auth.nebius.com`, `api.nebius.cloud` and `api.eu-north1.nebius.cloud` time out with a Cloudflare
**522** (Nebius appears to drop Cloudflare egress), while Token Factory (`api.tokenfactory.nebius.com`) works. So:

1. No Worker, cron or Workflow calls `/ai/v1/jobs` or the IAM token exchange. `NEBIUS_SA_CREDENTIALS` is **never** a Worker secret.
2. Scheduled work is Cloudflare cron -> Workflow calling Token Factory (and Tavily) only: the weekly rebuild (`WeeklyRebuild`).
3. NeMo Guardrails jobs (`certify`, `eval`, `import`) run on Nebius Serverless Jobs, started **on demand from a developer's CLI session** as
   `nebius --profile hackathon-jobs-sa` by `scripts/nebius-job.ts`. The job then POSTs its results to
   `https://localedition.pages.dev` (Cloudflare -> Cloudflare, signed with a per-job secret), which is the only direction that works.
4. Every doc, README line and UI string says each job is started from the CLI, on demand. Nothing claims a schedule that does not run.

This replaces approval 3 of 29 Oct 23:00 (docs/CLOUDFLARE.md) and the earlier GitHub `workflow_dispatch` plan (approvals 2 and 3).
The Worker was never deployed with the old path, so there was nothing live to undo. The 522 is also product feedback for Nebius
(docs/FEEDBACK.md, section 9).

## Where the code lives

Everything that talks to the control plane is under `scripts/` so the Worker tree (`src/`, `worker/`, `edge/`) cannot import it;
`tests/nebius/worker-isolation.test.ts` fails if a control-plane host, `NEBIUS_SA_CREDENTIALS`, `/ai/v1/jobs`, the job bundle or an import from
`scripts/` appears there.

| File | What |
|---|---|
| `scripts/nebius-job.ts` | The runner (`npx tsx scripts/nebius-job.ts <certify|eval|import>... [--app-url] [--csv-url] [--dry-run]`) |
| `scripts/nebius/runner.ts` | Argument parsing, the create request (per-job secret), the secret-free summary, log redaction |
| `scripts/nebius/cli.ts` | IAM token from `nebius --profile hackathon-jobs-sa iam get-access-token` (execFile, in memory only); job logs via `nebius ... ai job logs` |
| `scripts/nebius/jobs.ts`, `schemas.ts`, `errors.ts` | The REST jobs client, request and response shapes, typed errors |
| `scripts/nebius/job-spec.ts` | `buildLocalEditionJob`: the job's spec, `run.sh`, injected files |
| `scripts/nebius/job-bundle.generated.ts` | The job's files (generated by `npm run gen:job-bundle` from `jobs/` and `guardrails/localedition/`) |

Removed with this change (git history keeps them): the JWT signer, the credentials parser, the token exchange and cache, the Worker-side job
start (`src/server/workflows/nebius-start.ts`) and its weekly certify, poll and delete steps, and the one-off `live-check.ts` and `live-eval-check.ts`
(the runner generalises them).

## Running a job (the runner)

```sh
# env the developer loads (the runner prints neither): LE_JOB_SECRET = the app's shared secret, NEBIUS_API_KEY = the Token Factory key
npx tsx scripts/nebius-job.ts certify eval --dry-run   # validates the request with dryRun:true; creates and bills nothing
npx tsx scripts/nebius-job.ts certify eval             # one job: NeMo certify, then the red-team eval (one pip install)
npx tsx scripts/nebius-job.ts import --csv-url https://example.org/stores.csv
```

- **Token.** Obtained in-process with `execFile("~/.local/bin/nebius", ["--profile", "hackathon-jobs-sa", "iam", "get-access-token"])`; never printed,
  logged or written to disk. The runner never reads `~/.nebius/*` and never runs a command that shows a profile.
- **App.** `APP_URL` defaults to `https://localedition.pages.dev`; `--app-url` must be an https origin.
- **Secrets.** The job's `LE_JOB_SECRET` is the per-job secret `deriveJobSecret(shared, job name)` (`src/server/jobs/hmac.ts`, the same function the app
  verifies with in `src/server/jobs/job-auth.ts`: valid only for that name, on the job endpoints, within an hour of the timestamp in the name).
  `LE_JOB_SECRET` and `NEBIUS_API_KEY` are injected as files under `/opt/le-secrets/`, never as `environmentVariables`.
- **Run.** Creates `local-edition-<modes>-<yyyymmddhhmm>`, polls every 5 s, reads the logs with `nebius --profile hackathon-jobs-sa ai job logs`
  (secret values redacted), then deletes the job in a `finally` (also on Ctrl-C). Deletion is asynchronous (`DELETING` counts as done). It prints
  the job id, the states with seconds since start, and the exit code (0 only when the job ends `COMPLETED`).
- **App side.** The job posts with `TRIGGER=manual` and its name as the job id. `/api/jobs/results`, `/api/jobs/eval` and `/api/stores/import` record a
  `JobRun` (`trigger: "manual"`, `mode`, `nebiusJobId` = the job's name, `scriptSha`), one row per (mode, job name): a retried post overwrites its own row.
  The proof page and `/api/proof` read it. The weekly rebuild JobRun (`trigger: "cron"`, `nebiusJobId: null`) says certification is pending and runs on demand.

## Live REST proof (29 Oct 2026)

The one-off script that did this (`live-check.ts`) is folded into the runner. It created a tiny job, polled `GET` every 5 s until terminal, then deleted it.
Request body that worked (`POST https://api.nebius.cloud/ai/v1/jobs`):

```json
{"metadata":{"parentId":"project-e04yk83jbc00bwhyv60mbp","name":"local-edition-rest-check-20261029150128","labels":{"app":"local-edition","purpose":"rest-check"}},
 "spec":{"image":"python:3.12-slim","containerCommand":"python","args":"-c \"print('local-edition rest ok')\"","platform":"cpu-d3","preset":"2vcpu-8gb",
         "disk":{"type":"NETWORK_SSD","sizeBytes":"21474836480"},"timeout":"3600s","restartAttempts":"0"}}
```

Create returned an Operation with `resourceId` = job id in 7 s. States (seconds from start): `PROVISIONING@8 -> STARTING@52 -> IMAGE_PULLING@176 -> COMPLETED@193`.
`args` is one string that Nebius splits shell-style. Delete returned an Operation at once, but the record stayed `DELETING` for about 2 to 3 minutes:
treat `DELETING` as terminal for cleanup. Cost: about 20 s of billed run time, under $0.001.

## Endpoints used (base `https://api.nebius.cloud`)

| Call (client method) | Request | Response |
|---|---|---|
| Create (`jobs.create`) | `POST /ai/v1/jobs`, body `CreateJobRequest {metadata:{parentId,name,labels}, spec: JobSpec, dryRun?}` | `Operation`; **job id = `resourceId`**. `status` is set once finished: non-zero `status.code` is mapped to an error |
| Validate (`jobs.validate`) | same, `dryRun: true` | `Operation {id:"dry-run"}`; nothing created |
| Get (`jobs.get`) | `GET /ai/v1/jobs/{id}` (`?view=SECRET` returns injected file content: never used) | `Job {metadata{id,name,parentId,createdAt,labels}, spec, status{state, stateDetails{code,message}, startedAt, finishedAt}}` |
| Get by name (`jobs.getByName`) | `GET /ai/v1/jobs/get-by-name?parentId=&name=` | `Job` |
| List (`jobs.list`, `listAll`) | `GET /ai/v1/jobs?parentId=&pageSize=&pageToken=` | `{items: Job[], nextPageToken}` |
| Cancel (`jobs.cancel`) | `POST /ai/v1/jobs/cancel` body `{id}` | `Operation`. Stops the VM, deletes its disk, keeps the record |
| Delete (`jobs.delete`) | `DELETE /ai/v1/jobs/{id}` | `Operation`. Cancels first if running |

`JobSpec` fields we send: `image`, `containerCommand`, `args` (one string), `environmentVariables[{name,value}]`, `workingDir`,
`timeout` (`"3600s"`), `restartAttempts` (`"0"`), `platform`, `preset`, `disk {type:"NETWORK_SSD", sizeBytes:"21474836480"}`
(int64 as string), `injectedFiles[{containerPath, content: base64}]` (1 byte to 64 KiB each). Unused but available:
`registryCredentials`, `subnetId`, `publicIp`, `preemptible`, `pricingModel`, `volumes`, `ports`.
`JobStatus.State`: `PROVISIONING, STARTING, IMAGE_PULLING, RUNNING, COMPLETING, COMPLETED, CANCELLING, CANCELLED, DELETING, FAILED, ERROR`.
Terminal: `COMPLETED, FAILED, CANCELLED, ERROR` (`isTerminalState`). No `outputs`/bucket is ever set.

Retries: GET retries twice on 5xx or network errors (300 ms, 600 ms). **Create, cancel and delete are never retried by the client**.

## The Local Edition job (`buildLocalEditionJob`, `job-spec.ts`)

Pure function, no I/O. Name `local-edition-<modes joined by ->-<yyyymmddhhmm UTC>` (one mode: `local-edition-certify-202611020007`;
`certify` then `eval` in one job: `local-edition-certify-eval-202611020007`), parent `project-e04yk83jbc00bwhyv60mbp` (eu-west2), image
`python:3.12-slim`, `cpu-d3` / `2vcpu-8gb`, 20 GiB disk, `3600s` timeout (the platform minimum; billing is per second while running),
`restartAttempts: "0"`, labels `app=local-edition`, `modes=...`. Env: `APP_URL`, `TRIGGER` (`manual` default; the runner always sends `manual`), `JOB_NAME`
(certify.py records it as the job id), `PIP_ROOT_USER_ACTION`, `PYTHONUNBUFFERED`, plus any `env` you pass (import mode: `IMPORT_CSV_URL`).

**How the code ships without a custom image: `spec.injectedFiles`.** The OpenAPI also offers volumes (needs a bucket or filesystem,
which we must not create) and private registries; injected files need neither and the files are tiny. The runner injects, under `/opt/le`:

| File | Source |
|---|---|
| `run.sh` | `RUN_SH` in `job-spec.ts` |
| `certify.py`, `le_http.py`, `requirements.txt` | `jobs/` |
| `rails/*.py`, `rails/*.yml`, `rails/rails.co`, `rails/phrases.json` | `guardrails/localedition/`, `guardrails/tests/phrases.json` (certify.py looks in `./rails`) |

The architect's `scripts/gen-job-bundle.mjs` generates these as strings (`JOB_BUNDLE`, path relative to `/opt/le`) into
`scripts/nebius/job-bundle.generated.ts` (plus `JOB_PACK_B64`, the same files as one gzipped pack, which is what is actually injected because Nebius caps a request's injected files at 64 KiB in total). A test fails when the file is stale.
The container runs `bash /opt/le/run.sh certify eval`: `run.sh` exports secrets, `pip install -r requirements.txt` (nemoguardrails 0.24.1,
most of the 253 s spike), then runs `python certify.py --mode <m>` for each mode (every mode runs even if an earlier one failed;
the job exits non-zero if any did). Running both modes in one job pays the pip install once.

**Secrets.** Injected-file content is returned only by `GET ...?view=SECRET`, while `environmentVariables` values are plain spec fields. So by
default `LE_JOB_SECRET` (and `NEBIUS_API_KEY` for Lightning, which `certify` and `eval` need) are injected as files under
`/opt/le-secrets/<NAME>` and exported by `run.sh`. `secretDelivery: "env"` puts them in `environmentVariables` instead. A MysteryBox secret
(`environmentVariables[].mysteryboxSecret`) is the stronger option but needs a MysteryBox secret created first: not done.
The create request body carries the secrets: the client never logs bodies.

## Error mapping

`NebiusError { code, status?, retryable, nebiusCode? }`; `.toErrorBody()` gives `{ error, code }`. Messages never contain a token, JWT, key or
the raw upstream body (200-character sanitised excerpt of Nebius's `message`).

| `code` | When | Retry |
|---|---|---|
| `nebius_auth` | The CLI could not issue a token (not installed, profile signed out); API 401/403 (gRPC 16, 7) | No |
| `nebius_quota` | HTTP 429, gRPC 8, `ServiceError.notEnoughResources`, or a 400/412 whose message says quota or capacity | Later |
| `nebius_unavailable` | Network error, timeout (20 s API, 10 s exchange), 5xx, gRPC 13/14, non-JSON or wrongly shaped success body | Yes |
| `nebius_bad_request` | 400 not about quota (bad preset, unknown platform, validation errors), or `buildLocalEditionJob` input validation | No |
| `nebius_not_found` | 404 / gRPC 5 | No |
| `nebius_conflict` | 409 / gRPC 6: a job with that name exists | No |

The last three are additions to the three codes asked for. Observed: unknown platform in a project is a 400 `nebius_bad_request`, not quota.

Not routed through `src/server/http/fetchJson` (the Worker's provider layer): the client is session-only, and the create body carries secrets, which a record/replay layer must
never store. It takes a `fetchImpl` seam instead and never records.

## Limits and costs

- Service account `serviceaccount-e04jbjf4y2wmex8crk` is editor on `project-e04yk83jbc00bwhyv60mbp` (eu-west2, CPU jobs) and
  `project-e00fwfe5pr00k4s8jdngz0` (eu-north1, H100 GPU jobs, quota 16) and nothing else. `buildLocalEditionJob` takes `parentId`; no GPU job is planned for Local Edition (approval 4).
- Cost per run: about 4 to 5 minutes of `cpu-d3` 2vcpu-8gb, about $0.005 to $0.01 from the $25 AI Cloud balance (spike: about $0.005 for 253 s). A `certify` + `eval` job is about the same, since the pip install dominates; it costs that each time someone starts it, never on a schedule.
- The job never runs on a user request path; nothing here starts an endpoint, VM or GPU.
- Credentials file expires 31 Dec; the service account key rotation is the owner's, and after it the CLI profile `hackathon-jobs-sa` is re-created (nothing in Cloudflare holds the key).
